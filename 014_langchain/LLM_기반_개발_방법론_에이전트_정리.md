# LLM 기반 개발 방법론 — AI 에이전트·스킬·검증 워크플로 정리

> 작성: 2026-10-25(일) 기준. 질문 "AI 에이전트가 정확히 뭐야? Claude는 에이전트로 동작해?"에서 시작해, **이 저장소에서 실제로 LLM(Claude Code)과 일해 본 방식**을 방법론으로 정리했습니다.
> 표시 규칙: **[확인]** = 이 저장소에서 직접 보고·실행해 확인한 것, **[일반 지식]** = 일반적으로 알려진 내용(이 저장소에서 확인하지 않음), **[추정]** = 제 해석입니다.

## 1. 결론부터

- **AI 에이전트 = 목표를 받으면 스스로 "계획 → 도구 사용 → 결과 확인 → 다음 행동"을 반복해서 일을 끝내는 LLM 시스템**입니다. 챗봇은 한 번 묻고 한 번 답하지만, 에이전트는 **행동하고 그 결과를 보고 다시 판단**합니다.
- 이 저장소에서 Claude Code로 한 작업(노트북 읽기, 코드 실행으로 숫자 확인, 파일 수정, git 커밋)이 모두 에이전트 방식이었습니다 **[확인]**.
- 좋은 LLM 기반 개발은 "AI에게 맡긴다"가 아니라 **"컨텍스트를 주고, 실행으로 검증하고, 사람이 승인하는 순환"** 입니다(아래 5절).

## 2. AI 에이전트란

### 2.1 챗봇 vs 에이전트
| | 챗봇 | 에이전트 |
|---|---|---|
| 하는 일 | 질문에 답을 **말함** | 목표를 위해 **행동함** |
| 흐름 | 입력 1번 → 출력 1번 | 행동 → 관찰 → 행동 … (반복) |
| 도구 | 없음(또는 한정적) | 파일, 터미널, 검색, API 등 |
| 실수했을 때 | 틀린 말을 함 | **틀린 행동**을 할 수 있음(파일 수정, 명령 실행) |

### 2.2 구성: LLM + 도구 + 반복 루프 **[일반 지식]**
```text
        ┌────────────── 목표 ──────────────┐
        ▼                                   │
   ① 생각·계획 (LLM)                         │
        ▼                                   │
   ② 도구 사용 (파일 읽기, 코드 실행, git …)   │
        ▼                                   │
   ③ 결과 관찰 ── 목표를 달성했나? ── 아니오 ──┘
                        │ 예
                        ▼
                   사람에게 보고
```
- LLM은 "생각하는 부분", **도구는 손발**, 반복 루프가 "스스로 이어서 한다"를 만듭니다.

### 2.3 이 저장소에서의 실제 예 **[확인]**
| 목표(사용자 요청) | 에이전트가 한 행동 | 관찰 → 수정 |
|---|---|---|
| "`time` 오류 디버깅 설명" | 노트북 셀을 읽고, 같은 크기 배열로 `int(time+1)`을 실행 | `TypeError`를 재현 → 원인과 `time[-1]` 해결 확인 |
| "스펙트로그램 줄무늬가 안 보여" | STFT를 다시 계산해 `vmax`별로 그림을 그림 | 최댓값 0.0053 vs `vmax=0.2` 불일치 확인 |
| "커밋하고 push" | `git status`, 출력 점검, 주제별 add/commit/push | 목소리 재생기·경로 출력을 발견해 올라가는 사본에서 제거 |

## 3. 에이전트와 "고정된 흐름"의 차이 (수업 내용과 연결)

| 수업 | 내용 | 에이전트인가? |
|---|---|---|
| `014_langchain` LC01~03 | `prompt \| llm \| parser` 체인, 대화 메모리 | 흐름이 **미리 정해짐** → 워크플로 |
| `014_langchain` LC04 | `@tool`로 도구를 만들고 에이전트를 만드는 단계(비교 문서 작성 당시 에이전트 셀은 비어 있었음) | 에이전트를 배우는 자리 |
| `015_langgraph` | 노드·엣지·**조건 분기** | 분기가 있는 워크플로(분기 규칙은 사람이 정함: 질문 길이 > 20) |
| `016_rag` LangGraph 웹검색 챗봇 | 검색 노드 → 답변 노드 | 순서가 고정이라 **워크플로에 가까움 [추정]** |
- 구분의 핵심: **"다음에 무엇을 할지"를 코드(사람)가 정하면 워크플로, LLM이 그때그때 정하면 에이전트**입니다 **[일반 지식]**.
- LangGraph는 둘 다 만들 수 있는 틀입니다. 이전 부트캠프 비교 문서(`016_rag/LangChain_LangGraph_RAG_수업비교_modu_llm5_vs_음성AI.md`)에 `create_agent`, ReAct, ToolNode 같은 에이전트 내용이 이전 과정에는 있고 이번 과정에는 아직 없다고 정리해 두었습니다 **[확인]**.

## 4. 에이전트를 확장하는 방법

### 4.1 서브에이전트 **[일반 지식 + 확인]**
- 큰 일을 나눠 **별도의 도우미 에이전트**에게 맡기는 방식입니다. 장점은 병렬·분업, 단점은 도우미가 **처음부터 맥락을 다시 파악**해야 해서 비용이 크다는 점입니다.
- 이 세션에서는 서브에이전트를 띄우지 않고 한 에이전트가 처리했습니다 **[확인]**.

### 4.2 스킬(Skills) **[확인]**
- 스킬 = **"이런 요청이 오면 이 순서로 해"를 적어 둔 지침 파일**(`.claude/skills/<이름>/SKILL.md`). 에이전트의 **반복되는 업무 절차를 고정**하는 장치입니다.
- 이 저장소에 만든 스킬 3개:

| 스킬 | 절차의 핵심 |
|---|---|
| `notebook-review` | 학습 노트북을 `_강사님` 버전과 비교, 틀린 설명은 `학습내용_검증기록.md`에 기록(미확인 표기), 강사님 파일은 수정 금지 |
| `issue-log` | `개발환경_이슈노트.md`의 마지막 번호 +1로 같은 형식의 이슈 섹션 추가 |
| `commit-prep` | `.gitignore` 대상·내 목소리 음원(base64)·개인 경로·비밀값 점검 후 주제별 커밋 초안 → 승인 후 커밋 |
- `commit-prep`에는 노트북 출력을 검사하는 스크립트(`scan_notebook_outputs.py`)가 들어 있습니다.
- 한글 이름(`/노트북리뷰` 등)이 슬래시 명령으로 인식되는지는 **확인하지 못했습니다.** 폴더 이름은 영문으로 만들고 설명에 한글 트리거를 적어 두었습니다.

### 4.3 "superpowers"
- 이 세션에는 설치되어 있지 않고, 정확히 무엇인지는 **확인하지 못했습니다.** Claude Code에 스킬 모음을 추가하는 서드파티 플러그인으로 알고 있지만 기억에 의존한 것이라 틀릴 수 있습니다 **[일반 지식, 미확인]**. 설치 전에는 공식 README를 읽고, 어떤 파일을 건드리는지 확인하는 것이 안전합니다.

## 5. 이 저장소에서 쓴 LLM 기반 개발 방법론 **[확인]**

| 원칙 | 이 저장소의 구체적인 장치 | 왜 필요한가 |
|---|---|---|
| **① 컨텍스트를 파일로 고정** | `CLAUDE.md`(환경·폴더 규칙·노트북 변형 규칙), `개발환경_이슈노트.md` | 대화가 길어져도 규칙(voice-ai만 사용, numpy 1.26.4 유지, `_강사님` 수정 금지)을 잊지 않게 |
| **② 말하기 전에 실행으로 확인** | 설명에 나오는 숫자는 직접 실행한 값(예: `(257, 247)`, `0.1494`), 못 한 것은 "추정/미확인" 표시 | 사용자가 **설명으로 공부**하므로 틀린 설명은 그대로 학습됨 |
| **③ 오류 기록** | `학습내용_검증기록.md`(고친 오류, 확정 못 한 것) | 같은 실수 반복 방지(예: "440 Hz가 도" → 도는 262 Hz) |
| **④ 원본 보호** | `_강사님` 파일 수정 금지, 코드는 요청 전에 바꾸지 않음(설명만 추가) | 비교 기준이 흔들리지 않게 |
| **⑤ 작은 단위 + 사람 승인** | 주제별 커밋, 커밋·push는 "네, 해줘" 확인 후 | 되돌리기 쉬운 단위로, 외부에 공개되는 행동은 사람이 결정 |
| **⑥ 공개 전 점검** | `.env`·`data/`·`results/` ignore, 노트북 출력의 목소리 재생기·`/Users/…` 경로 제거 | 공개 저장소는 한번 올라가면 되돌리기 어려움 |
| **⑦ 반복 업무는 스킬로** | 위 4.2의 스킬 3개 | 매번 같은 절차를 설명하지 않게 |

## 6. 에이전트의 한계와 대응 **[확인된 사례 포함]**

| 한계 | 이 저장소에서 있었던 일 | 대응 |
|---|---|---|
| **잘못된 대상에 행동** | 폴더에 같은 접두어의 `_강사님` 파일이 새로 생겼을 때, 파일을 순서(`glob()[0]`)로 찾는 바람에 **강사님 파일에 설명 셀을 잘못 넣음**(발견 즉시 되돌림) | 항상 **정확한 파일명**을 지정, `CLAUDE.md`에 주의사항 기록 |
| **그럴듯한 오설명** | "440 Hz가 도"(이 수업의 도는 262 Hz), "60 Hz 이내 두 음이 섞인다"(측정한 폭은 125 Hz) | ②③: 실행으로 확인하고 고친 뒤 기록 |
| **비용·시간** | 서브에이전트는 맥락 재파악 비용이 큼 | 꼭 필요할 때만 사용 |
| **권한·안전** | 파일 수정, git, 외부 공개 | 사용자 승인, 점검 스킬 |
- 정리: **에이전트의 실수를 막는 것은 모델의 똑똑함보다 "검증 장치와 사람의 승인"** 입니다 **[추정]**.
