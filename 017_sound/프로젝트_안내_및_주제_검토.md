## 4. 평가와 코멘트

### 4.1 강사님 기준과의 적합성
- **OpenAI API 기반** 범주에 들어갑니다. 수업 `013_openai_api`에서 이미 **STT(`transcribe_korean`)와 TTS(`text_to_wav`)** 를 다뤘고 **license-key가 제공**됩니다 **[확인]**.
- 음성 과정에서 이어서 배울 것(이 저장소 README 기준 **[확인]**): Whisper 음성 인식, **WER·CER와 오류 분석**, 음성 합성의 전체 흐름. 이 내용이 아이디어의 **채점(WER/CER)** 과 직접 연결됩니다.
- **위험:** 외부 서비스(발음 평가 API, 음악 인식 API, 가사 API, 음악 카탈로그 API)는 **제공되는 키가 없고 약관·요금·지원 언어가 불확실**합니다. 40시간에서 **키 발급과 약관 확인에만 시간이 새기 쉽습니다.** 필수 기능은 **수업에서 제공받는 OpenAI API만으로** 동작하도록 설계하는 것을 권합니다 **[추정]**.

### 4.2 아이디어의 강점
- **문제의 출처가 분명**합니다(좋아하는 노래의 뜻을 알고 따라 부르고 싶다). 발표에서 "왜 만들었나"를 설명하기 쉽습니다.
- **듣기(TTS → 받아쓰기)와 말하기(녹음 → STT) 두 가지 음성 활용**을 모두 쓰고, 수업의 STT·TTS·WER/CER·음향 처리(017)와 겹칩니다.
- 장표의 포트폴리오 목적(경험 증명, 개발 프로세스 이해)에 맞춰 **"실험과 평가를 포함한 음성 AI 프로젝트"** 로 만들 수 있습니다.

### 4.3 위험과 해결 방향
| 위험 | 설명 | 해결 방향 |
|---|---|---|
| **데이터(가사) 확보 + 저작권** | 가사와 음원은 저작권 대상일 수 있음. 이 저장소는 공개 | **직접 만든 예문**, 공개·자유 이용이 확인된 문장으로 시작. 상업 가사/음원은 **저장소·발표 자료에 넣지 않음**. "개인 학습용 입력 기능"으로만 두는 안은 약관을 확인한 뒤 판단 |
| **STT 일치 ≠ 발음 정확** | STT는 문맥으로 의도한 문장을 맞힐 수 있음 | 채점 지표를 **"단어 일치도(WER/CER)"** 로 이름 붙이고 "발음 평가"라고 주장하지 않음 |
| **범위 초과** | 검색·가사·TTS·받아쓰기·녹음·평가·PWA를 모두 넣음 | MVP를 **핵심 흐름 하나**로 제한(아래 4.4) |
| **채점의 정의** | 점수의 의미가 모호함 | 단어 일치도 / 발음 정확도 / 노래 실력을 **구분**해서 앞의 둘만 다룸 |
| **API 의존** | 한도·키·모델 이름이 바뀔 수 있음 | 수업 키로 **1일차에 실제 호출 테스트**, 대체 경로(직접 입력, 녹음 파일 업로드) 준비 |

### 4.4 제안 MVP (노래 기능은 모두 확장)
```text
[입력] 학습 문장 선택/입력 (직접 만든 예문, 사용 권한이 확인된 문장)
   │
   ├─ 학습 1 (듣기): OpenAI TTS로 재생 → 사용자가 받아쓰기 → 정답과 비교해 WER/CER·틀린 단어 표시
   │
   └─ 학습 2 (말하기): 사용자가 문장을 읽어 녹음 → STT로 인식 → 기준 문장과 WER/CER 비교
[추가 실험 1개] TTS 음성과 내 녹음의 차이를 파형·길이·SR·Mel로 비교 (수업 017 연결)
[확장] 노래 검색(텍스트) → 소리 검색 → 노래 채점
```
- **받아쓰기(학습 1)** 는 외부 STT가 없어도 되고, 키보드 입력을 정답과 비교하는 것이라 **가장 안전한 핵심 기능**입니다 **[추정]**.

### 7.3 WER·CER 한눈에 (직접 구현·실행해 확인한 것)
**정의**
- 정답(reference)과 인식 결과(hypothesis)를 비교해 **최소 수정 횟수**(Levenshtein 편집 거리)를 셉니다 **[일반 지식]**.
  - **S** 치환(바뀜), **D** 삭제(빠짐), **I** 삽입(더 붙음), **N** 정답의 전체 단위 수
  - **오류율 = (S + D + I) ÷ N**
- **WER**(Word Error Rate)은 **단어 단위**, **CER**(Character Error Rate)은 **글자 단위**입니다. 한국어에서 "단어"는 보통 **띄어쓰기로 나뉜 어절**로 셉니다(제 구현 기준).
- 0에 가까울수록 정확합니다. 삽입이 많으면 **1을 넘을 수도** 있습니다 **[일반 지식]**.

**손계산 예 (직접 계산해 확인)**
| 정답 | 인식 | WER | CER (공백 제외 글자) |
|---|---|---|---|
| 오늘 날씨가 좋아요 | 오늘 날씨 좋아요 | **1/3 = 0.333** (치환 1: 날씨가→날씨) | **1/8 = 0.125** (삭제 1: '가') |
| 오늘 날씨가 좋아요 | 오늘 날씨가 좋아요 | 0 | 0 |
| 오늘 날씨가 좋아요 | 내일 날씨가 정말 좋아요 | 2/3 = 0.667 (치환 1 + 삽입 1) | 4/8 = 0.5 (치환 2 + 삽입 2) |
- **한국어에서 WER과 CER이 크게 다른 이유**: 조사·어미가 어절에 붙어 있어서 **'날씨가' → '날씨'** 처럼 한 글자만 달라도 **어절 하나가 통째로 틀린 것**이 됩니다. 그래서 **CER이 더 세밀한 지표**이고, 한국어 평가에서는 **CER을 함께 보는 것**이 좋습니다 **[제 판단, 일반적인 관행 여부는 미확인]**.

**꼭 정하고 가야 하는 규칙: 정규화(비교 전에 문장을 같은 모양으로 맞추기)**
- Whisper는 **쉼표를 마음대로 넣습니다.** 정규화 없이 비교하면 **같은 문장인데도 틀린 것으로 셉니다.** 아래 5개 WAV로 직접 확인한 결과입니다.

**실제 결과 (이 저장소 `data/speech/`의 WAV 5개를 Whisper tiny(int8, 한국어, `beam_size=1`)로 인식 → `speech_manifest.json`의 정답과 비교)**
| ID(끝 4자리) | 인식에서 달라진 곳 | WER (구두점 제거 후) | CER |
|---|---|---|---|
| 0001 | 없음 (정답과 동일) | 0.000 | 0.000 |
| 0006 | 쉼표만 추가 | **0.000** | 0.000 |
| 0008 | `자료의`→`자료에`, 쉼표 추가 | 0.059 | 0.021 |
| 0012 | `알맞은`→`알마진`, 쉼표 추가 | 0.077 | 0.056 |
| 0014 | `쉬었다가`→`수였다가`, 쉼표 추가 | 0.250 | 0.167 |
| **5개 합산** | | **0.060 (3/50)** | **0.034 (5/146)** |
- **구두점을 지우지 않고 그대로 비교하면 같은 5개의 합산 WER이 `0.200`(10/50)** 으로 나옵니다(쉼표 붙은 어절을 "다른 단어"로 세기 때문). **정규화 규칙에 따라 점수가 3배 이상 달라진다**는 뜻입니다.
- 이 5개는 **수업에서 제공한 음성(깨끗한 발음)** 이라 결과가 좋은 편입니다. **내 목소리·소음·빠른 말에서는 달라질 수 있습니다(미확인)**.
- 실행에 쓴 별도 스크립트는 이 저장소 노트북에 넣지 않았습니다(아래 코드가 같은 계산).

**직접 구현 코드(검증함, 약 20줄)**
```python
import re
def edit_distance(ref, hyp):
    """Levenshtein 거리와 (S 치환, D 삭제, I 삽입) 개수를 함께 구함"""
    n, m = len(ref), len(hyp)
    dp = [[(0,0,0,0)]*(m+1) for _ in range(n+1)]          # (총비용, S, D, I)
    for i in range(1,n+1): dp[i][0] = (i,0,i,0)
    for j in range(1,m+1): dp[0][j] = (j,0,0,j)
    for i in range(1,n+1):
        for j in range(1,m+1):
            if ref[i-1]==hyp[j-1]: dp[i][j] = dp[i-1][j-1]
            else:
                c,s,d,ins = dp[i-1][j-1]; sub  = (c+1,s+1,d,ins)
                c,s,d,ins = dp[i-1][j];   dele = (c+1,s,d+1,ins)
                c,s,d,ins = dp[i][j-1];   inse = (c+1,s,d,ins+1)
                dp[i][j] = min(sub,dele,inse)
    return dp[n][m]

normalize = lambda t: re.sub(r'[.,!?~\-]', '', t).strip()   # 구두점 제거 (규칙은 직접 정해야 함)
def wer(ref, hyp):
    r, h = normalize(ref).split(), normalize(hyp).split()
    return edit_distance(r, h)[0] / len(r)
def cer(ref, hyp):
    r, h = list(normalize(ref).replace(' ','')), list(normalize(hyp).replace(' ',''))
    return edit_distance(r, h)[0] / len(r)
```
- 라이브러리로는 `jiwer`가 널리 쓰인다고 알고 있으나 **이 환경(`voice-ai`)에는 설치되어 있지 않고 직접 확인하지 않았습니다 [일반 지식, 미확인]**. 설치 전 `pip install --dry-run`으로 확인하세요(`numpy` 1.26.4 유지, CLAUDE.md 참고).

**연습 순서 제안**
1. 위 손계산 3개를 종이로 풀고 코드 결과와 비교.
2. 5강 정답 5개 vs 7강 노트북에서 `model.transcribe`한 결과로 WER/CER 구하기(7강 노트북 3번 셀의 경로만 바꿔 반복).
3. **내 목소리로 같은 문장 3~5개**를 녹음해 같은 방법으로 비교(WER이 어떻게 달라지는지 기록 — 프로젝트의 "비교 실험" 재료).
4. 정규화 규칙(구두점·띄어쓰기·숫자 표기)을 바꿔 보며 점수가 어떻게 달라지는지 기록.

### 7.4 TTS 구조(음향 모델·보코더) 한눈에 — **[일반 지식] 개념 정리, 수업에서 확인하지 않음**
```text
텍스트  →  ①텍스트 전처리  →  ②음향 모델(acoustic model)  →  ③보코더(vocoder)  →  음성 파형
"안녕"     (숫자·약어 읽기,     글자/발음 → Mel 스펙트로그램         Mel → 실제 소리(파형)
            발음 기호 변환)      (시간에 따른 소리 모양을 예측)
```
| 단계 | 하는 일 | 수업과의 연결 |
|---|---|---|
| ① 텍스트 전처리 | 숫자·약어를 읽는 글자로 바꾸고, 글자를 발음 단위로 바꿈 | 5강의 토큰화와 비슷한 "글 → 번호/단위" 단계 |
| ② **음향 모델** | 텍스트(발음)를 받아 **Mel 스펙트로그램**(시간별 주파수 모양)을 예측 | **4강의 Mel/Log-Mel이 이 단계의 출력** |
| ③ **보코더** | **Mel 스펙트로그램을 실제 파형(소리)으로 복원** | **STFT·Mel의 반대 방향**(3~4강에서 소리→Mel을 했다면 이것은 Mel→소리) |
- **STT와 TTS는 서로 반대 방향**입니다: STT = 소리 → Mel → 텍스트, TTS = 텍스트 → Mel → 소리. 그래서 **Mel이 두 쪽의 공통 중간 표현**입니다.
- 이 세 단계를 **하나의 모델로 합친 "종단간(end-to-end)" 모델**도 있습니다.
- 대표적인 이름(검색 키워드로 활용): 음향 모델 **Tacotron 2, FastSpeech 2**, 보코더 **WaveNet, HiFi-GAN**, 종단간 **VITS** **[기억에 의존한 일반 지식, 발표에 쓰기 전에 논문·공식 문서로 확인 필요]**.
- **OpenAI TTS API의 내부 구조는 공개된 정보를 확인하지 못했습니다 [미확인]**. 프로젝트에서는 **API를 호출하는 블랙박스**로 쓰며, 위 구조는 "TTS가 일반적으로 이렇게 구성된다"는 개념 설명용입니다.

### 7.5 이 아이디어(노래로 외국어 학습)와의 연결
| 프로젝트 부분 | 필요한 지식 | 수업에서 | 보완 |
|---|---|---|---|
| TTS로 문장 들려주기 | API 호출 방법 | `013_openai_api` **[확인]** | 구조(7.4)는 개념만 |
| 받아쓰기·읽기 채점 | **WER/CER** | **없음** | **7.3으로 자습(필수)** |
| 내 녹음 → STT | Whisper 사용법 | 7강, `013` **[확인]** | 정규화 규칙 정하기 |
| TTS 음성 vs 내 녹음 비교 실험 | Mel·파형 시각화 | 3~4강 **[확인]** | 이미 가능 |
- **"STT가 맞게 인식했다 = 발음이 정확하다"가 아님**을 계속 주의합니다(4.3절). Whisper가 문맥으로 **틀린 발음도 올바른 문장으로 고쳐 적을** 수 있어서, WER/CER은 **"단어 일치도"** 이지 **발음 평가가 아닙니다 [일반 지식 + 4.3절]**.

> 아래는 **초안**입니다. 강사님 양식·분량은 모르고, 숫자는 **제 제안값 [추정]** 이라 본인 상황에 맞게 조정하세요. LLM 서비스를 사용해 작성하는 것이 허용된다고 하니, 8.5의 요청문을 활용할 수 있습니다. LLM이 쓴 숫자·사실은 **반드시 직접 확인**하세요(이 문서의 이전 LLM 답변들에서도 확인되지 않은 주장이 있었습니다, 3.3절).

**1. 프로젝트 개요**
- **목적**: 외국어(또는 한국어) 문장을 **듣고 받아쓰기**하고 **따라 읽은 녹음을 음성 인식으로 확인**해, **정답 문장과의 일치도(WER/CER)** 와 **틀린 부분**을 보여 주는 연습 도구를 만든다. (발음 점수가 아니라 **문장 인식 일치도**임을 명시)
- **범위(포함)**: 연습 문장 10개(직접 작성), TTS로 문장 재생, 받아쓰기 입력 채점, 녹음 → STT → 정답 비교, 틀린 단어·글자 표시, 연습 기록 저장, 조건 비교 실험 1개.
- **범위(제외)**: 노래·가사 자동 처리, 발음·억양·음정 평가, 실시간 스트리밍, 다수 사용자 계정, 모델 추가 학습.
- **성공 기준(SMART, 측정 가능)** — **L1/L2/L3 구분은 해석이 불확실해 "필수·확장·도전"으로 임시 표기** [추정]
  | 단계 | 목표 | 측정 방법 |
  |---|---|---|
  | **L1 필수** | 연습 문장 10개에 대해 **녹음 업로드 → STT → WER·CER 표시**가 오류 없이 동작 | 문장 10개 × 3회 실행, 실패 0회, 정규화 규칙을 문서에 명시 |
  | **L2 확장** | **TTS 받아쓰기 흐름** + **틀린 부분 하이라이트** + **연습 기록 저장·일치율 그래프** | 기능 3개 시연, 기록 CSV 30행 이상 |
  | **L3 도전** | **조건 비교 실험**(예: 조용한 환경 vs 잡음, 모델 크기 tiny vs base 중 1개)의 WER/CER 표와 해석 | 조건당 문장 10개, 결과 표 + 그래프 1개 |
- 기한: **프로젝트 종료일 전까지(정확한 날짜 확인 필요)**.

**2. 기술 스택** — Python, `faster-whisper`(7강, 로컬 STT) 또는 OpenAI STT(013), OpenAI TTS(013), NumPy·SciPy·matplotlib(017), Pandas(CSV 기록), `difflib`(틀린 부분 표시, 파이썬 표준 라이브러리), (선택) 화면 도구는 **수업에서 쓰지 않았으므로 필요 여부를 질문 후 결정**(`ipywidgets` 또는 Streamlit 등 **[미확인]**).

**3. 프로그램 구조(강조 항목)**
```text
[연습 문장 목록(CSV)]
        ├─ 듣기 연습: TTS로 재생 → 사용자 받아쓰기(텍스트 입력) ─┐
        └─ 읽기 연습: 마이크/파일 녹음 → 16kHz 모노 변환 → STT ───┤
                                                                   ▼
                                       정규화(구두점·공백) → WER/CER 계산 → 틀린 부분 표시
                                                                   ▼
                                               연습 기록(CSV) 저장 → 일치율 그래프, 실험 표
```
- 구성 요소별 파일(예): `sentences.csv`, `tts.py`, `stt.py`, `scoring.py`(WER/CER), `app` 화면 코드, `results/`(기록·그래프).

**4. Data 수집 방법(강조 항목)**
- **연습 문장**: **직접 작성한 예문** 10개(저작권 문제 없음). 상업 가사·음원은 사용하지 않음.
- **음성**: ① **내가 직접 읽은 녹음**(개인 음성은 공개 저장소에 올리지 않음, 이 저장소의 `.gitignore` 규칙 유지), ② **TTS로 생성한 음성**(OpenAI API 약관·사용 한도는 **확인 필요**), ③ 수업 제공 WAV 5개(기능 확인용, 사용 범위 확인).
- 정답은 **내가 쓴 문장 그대로**이므로 별도 라벨링이 필요 없음.

**5. 도출 결과물**
- 동작하는 연습 도구(시연), **WER/CER 계산 코드와 정규화 규칙 문서**, **조건 비교 실험 결과(표·그래프)**, **README(사용법·한계)**, 발표 자료. 한계: "발음 정확도 평가가 아님, 인식 모델 오류가 결과에 영향".

**6. 일정 관리 (36시간 = 9일 × 4시간 가정, [추정])**
| 일차 | 할 일 |
|---|---|
| 1 | 환경 점검(마이크 녹음, Whisper 로컬 로드·OpenAI TTS/STT 호출 테스트·키 한도 확인), 연습 문장 10개 확정, **Notion 페이지 개설**, WER/CER 함수 이식 |


- **우려는 타당합니다.** STT·TTS API를 호출해 이어 붙이는 것만으로 끝나면 깊이가 얕습니다.
- 깊이는 세 곳에서 만들 수 있고 **계획서에 반영**했습니다.
  1. **평가 설계**: 정규화 규칙·언어별 단위(WER/CER)에 따른 점수 변화(이미 같은 5개 WAV에서 0.060 대 0.200으로 확인한 현상)를 **체계적으로 비교**.
  2. **실험**: 조용한 환경 vs 잡음, 모델 크기, **"노래에서 텍스트 추출"이 실제로 어려운지 데이터로 검증(L3-a)**, **STT 신뢰 지표와 실제 오류의 관계(L3-b)**.
  3. **직접 학습 컴포넌트(L3-c)**: **녹음 품질 분류기**를 Log-Mel + 소형 DNN/CNN으로 학습해 STT 전에 경고하는 기능으로 연결 → B안의 "직접 학습" 경험을 **내 주제 안에서** 얻습니다.
- 평가 기준을 강사님이 알려 주지 않았으므로(미확인) **완성도(L1~L2)와 깊이(L3)의 비중**은 면담에서 확인하는 것이 좋습니다.

### 8.9 FFT·STFT·Log-Mel을 내 프로젝트에 활용하는 방안 (2026-10-30)
> 질문: "내 프로젝트에 FFT, STFT, (Log-)Mel 등을 활용할 수 있는 방안은 없을까?"

**먼저 알아둘 연결점 [확인]** — 7강에서 쓰는 Whisper는 **내부에서 Log-Mel 특징을 만들어 입력**으로 씁니다(7강 노트북: "음성 읽기·16kHz 변환·Log-Mel 특징 추출을 내부에서 처리"). `faster-whisper`의 특징 추출기를 열어 값을 확인했습니다.

| | 4강에서 한 것 | Whisper 내부 (확인) |
|---|---|---|
| 창 크기 `n_fft` | 512 | **400** (25ms) |
| 이동 `hop` | 128 (8ms) | **160** (10ms) |
| Mel 개수 | 40 | **80** (`mel_filters` 모양 `(80, 201)`) |
| 4.9초 음성의 출력 | `(40, 프레임)` | **`(80, 490)`** |
| 한 번에 보는 길이 | — | 30초(`chunk_length`), 프레임 3000개 |
- 발표에서 **"수업에서 배운 STFT·Mel이 Whisper 안에서 이렇게 쓰인다"** 는 연결 근거로 쓸 수 있습니다.

**활용 방안 (단계별)** — 시간 추정은 **[제 추정]**

| 단계 | 활용 | 쓰는 수업 내용 | 설명 | 시간 |
|---|---|---|---|---|
| **L1 보조** | **녹음 품질 점검** | 1·2강(RMS, 최대 진폭, 무음 비율, 클리핑) | STT 전에 "너무 작아요 / 잡음이 많아요 / 소리가 잘렸어요" 경고. 새로 배울 것이 거의 없고 02 노트북 코드를 재사용 | 1~2h |
| **L2 옵션** | **스펙트로그램 비교 화면** | 4강(STFT, Mel 필터) | TTS 음성과 내 녹음의 Log-Mel을 나란히 표시. **시각 참고 정보**이며 그림이 다르다고 발음이 틀렸다고 판정하지 않음(위험 요소에 명시) | 2~3h |
| **L2/L3 옵션** | **발화 구간·속도·쉼 분석** | 3강(STFT), 2강(구간 자르기) | 에너지로 말하는 구간과 쉬는 구간을 찾아 **발화 속도**(글자 수 ÷ 발화 시간)·**쉼 횟수/길이**를 TTS와 비교. "유창성 참고 지표"로만 보여주고 점수화는 조심 | 3~4h |
| **L3 실험** | **잡음 견고성 실험**(SNR vs WER/CER) | 2강(잡음 섞기), 3강(STFT) | 8.10~8.11 참고. **가장 추천** | 4~5h |
| **L3 실험** | **노래 구간 인식**(L3-a) | 3·4강 | 말과 노래의 스펙트로그램(음의 길이·배음·피치 변화)을 비교하고, 노래가 STT에 더 어려운지는 **가설로 두고 실험으로 확인**(미확인) | 6h |
| **L3-c** | **녹음 품질 분류기 직접 학습** | 4·5·6강 | Log-Mel + 소형 DNN/CNN. 입력으로 4강의 40 Mel과 Whisper의 80 Mel을 **비교**해 볼 수 있음. 데이터 필요(8.12) | 10h |

**잡음 실험의 첫 결과 (내가 먼저 돌려 본 값, 단일 실행) [확인]**
수업 제공 한국어 WAV 5개(깨끗한 합성 음성)에 흰 잡음(가우시안)을 **신호 대 잡음비(SNR)** 기준으로 섞고 Whisper tiny(int8, CPU)로 인식해 정답과 비교. 구두점 제거, 5개 합산.

| 조건 | 합산 WER | 합산 CER |
|---|---|---|
| 깨끗한 원본 | 0.060 | 0.034 |
| SNR 20 dB | 0.100 | 0.048 |
| SNR 10 dB | 0.300 | 0.171 |
| SNR 5 dB | 0.560 | 0.397 |
| SNR 0 dB | **0.960** | **0.932** |
- 잡음이 클수록 **단조롭게 나빠졌고**, 10 dB 근처에서 급격히 떨어졌습니다. 0 dB에서는 거의 인식하지 못했습니다. 계산 시간도 달랐습니다(깨끗한 원본 5개 8초, 0 dB 185초 — 이유는 확인하지 못함).
- **한계**: 이 PC·tiny·`int8`·이 5개 파일·인위적인 흰 잡음에서 나온 값입니다. 실제 카페·거리 소음, 다른 사람 목소리, 다른 모델에서는 달라질 수 있습니다 **[미확인]**.

**추천 순위 [제 판단]**: ① 잡음 견고성 실험(baseline이 이미 있고 FFT·STFT·SNR을 직접 사용) → ② 녹음 품질 점검(L1 보조, 비용 거의 없음) → ③ 스펙트로그램 비교 화면(수업 개념이 눈에 보임) → ④ L3-c.

### 8.10 이런 확인은 내가 직접 해보는 것이 맞습니다 — 방법 (내가 한 방법 포함)
> 질문: "FFT 특징 추출기를 열어 확인하고 잡음 실험을 한 것은 내가 내 프로젝트에서 해봐도 되는 것 아닌가? 왜 너가 다 하고 결과만 알려주나?"

**답: 네, 직접 해보는 것이 맞고, 프로젝트에서는 그래야 합니다.**
- **내가 먼저 한 이유**: 추천하기 전에 "실제로 돌아가는지, 얼마나 걸리는지"를 빠르게 확인하려고 했습니다. 그런데 **결과만 전달하면 네가 직접 겪어 보는 과정(왜 이렇게 되는지 이해, 오류 만나기, 값 의심하기)이 빠집니다.** 평가에서도 **직접 만든 실험과 해석**이 더 의미가 있습니다.
- **내 값은 참고용 baseline**입니다(이 PC, 5개 파일, 단일 실행). **프로젝트 결과로 쓰는 값은 네가 직접 돌려서 얻은 값**이어야 합니다. 이 문서의 숫자는 **네 결과가 대략 이 정도 범위인지 비교하는 용도**로만 쓰세요.
- 앞으로 이런 확인은 **"방법 → 네가 실행 → 나는 해석·오류 확인"** 순서로 진행하는 것을 제안합니다. 내가 실행한 스크립트는 저장소에 저장하지 않았고, **아래 코드를 직접 입력해 실행**해 보세요(모두 내가 한 방법이고 실제로 실행해 확인한 코드입니다).

**방법 ① Whisper가 내부에서 만드는 특징 열어 보기**
```python
from faster_whisper.feature_extractor import FeatureExtractor
from faster_whisper.audio import decode_audio

fe = FeatureExtractor()
print(fe.__dict__)        # n_fft, hop_length, sampling_rate, mel_filters(모양) 등 설정이 보임
x = decode_audio("data/speech/1272-128104-0001.wav", sampling_rate=16000)   # 16kHz 모노 float32로 읽음(m4a도 가능)
mel = fe(x)
print(mel.shape)          # (80, 프레임 수): 80 Mel × 10ms 간격 프레임
```
- 확인 포인트: **내가 4강에서 만든 `(40, 프레임)` 배열과 비교**(창 크기·이동·Mel 개수가 어떻게 다른지). 이 방법은 "라이브러리 내부 값을 `__dict__`나 `.shape`로 직접 열어 본다"는 일반적인 확인 습관입니다.

**방법 ② 잡음을 SNR 기준으로 섞기**
```python
import numpy as np

def add_noise(x, snr_db, rng):
    """깨끗한 신호 x에 흰 잡음을 더해 신호 대 잡음비(SNR)가 snr_db가 되게 만듦"""
    noise = rng.normal(size=len(x)).astype("float32")
    noise *= np.sqrt(np.mean(x**2) / (10 ** (snr_db / 10)) / np.mean(noise**2))
    return (x + noise).astype("float32"), noise

rng = np.random.default_rng(0)
noisy, noise = add_noise(x, 10, rng)
print(10 * np.log10(np.mean(x**2) / np.mean(noise**2)))    # 검증: 10.0 에 가까워야 함 (내가 돌려 보니 10.0)
```
- **SNR(dB) = 10 × log10(신호 파워 ÷ 잡음 파워)**. 값이 작을수록 잡음이 큽니다(0 dB = 신호와 잡음의 파워가 같음). **섞은 뒤 SNR을 다시 계산해 목표와 맞는지 검증**하는 단계를 꼭 넣으세요.

**방법 ③ 배열을 그대로 인식하고 채점하기**
```python
segments, _ = model.transcribe(noisy, language="ko", task="transcribe", beam_size=1)   # 파일 경로 대신 numpy 배열도 가능
hyp = "".join(s.text for s in segments).strip()
# 이후 7.3절의 normalize / wer / cer 함수로 정답과 비교
```

**방법 ④ 조건을 바꿔 반복하고 합산하기**
- 조건: `[None, 20, 10, 5, 0]`(None = 깨끗한 원본), 문장마다 `(S + D + I)`와 `N`을 **모아서 합산**한 뒤 `합산 오류 ÷ 합산 N`으로 계산(문장별 비율의 평균이 아님).
- **시간을 재세요**(`time.time()`): 잡음이 클수록 오래 걸릴 수 있습니다(내 값: 0 dB에서 185초).

**방법 ⑤ 같은 조건을 여러 번 반복하기 (중요, 내가 이번에 확인한 사실)**
- 잡음은 **무작위**라서 실행할 때마다 값이 달라집니다. 같은 SNR이라도 잡음 시드를 바꾸면 결과가 다음처럼 달랐습니다.

  | 조건 | 1회차 | 2회차(잡음 시드가 다름) |
  |---|---|---|
  | SNR 10 dB 합산 WER | 0.300 | **0.260** |
  | SNR 10 dB 합산 CER | 0.171 | 0.164 |
  | SNR 5 dB 합산 WER | 0.560 | **0.620** |
  | SNR 5 dB 합산 CER | 0.397 | 0.493 |
- 즉 **단일 실행 값이 흔들립니다**: 이 5개 파일에서 같은 SNR의 두 번 실행 차이는 **WER 기준 0.04~0.06, CER 기준 0.01~0.10**이었습니다(관찰한 두 번의 비교일 뿐, 흔들림의 크기를 일반화할 수는 없음). 그래서 **시드를 바꿔 3회 이상 반복하고 평균(과 범위)을 보고**해야 합니다. 이 점이 이 실험의 "직접 해봐야 아는" 부분입니다.

- [ ] 섞은 뒤 SNR을 **다시 계산해 검증**했다
- [ ] **시드를 고정**하고 바꿔서 **여러 번 반복**했다(평균·범위 기록)
- [ ] 정규화 규칙(구두점 등)을 **고정**하고 문서에 기록했다
- [ ] 처리 시간과 사용한 모델(tiny/base, `int8`)을 기록했다
- [ ] **원본 음성 파일은 건드리지 않고** 배열에서만 잡음을 섞었다

### 8.11 L3 잡음 실험은 자명한가? 의미가 있는가?
> 질문: "잡음 vs 음성을 비교하는 실험이 무척 자명한 것 아닌가? 잡음이 섞이면 당연히 인식이 어렵다. 강사님이 쓸 만한 잡음 제거 모듈이 있다고 하셨는데, 이 실험이 왜, 어떻게 의미가 있는가?"

**결론: "잡음이 크면 나빠진다"만 확인하는 실험이면 자명합니다.** 의미는 **자명하지 않은 부분을 질문으로 만들 때** 생깁니다.

**자명한 것 vs 자명하지 않은 것**
| 자명한 것(방향) | 자명하지 않은 것(정량·결정) |
|---|---|
| SNR이 낮을수록 오류가 늘어난다 | **어느 SNR에서 무너지는가?** 위 결과는 20 → 10 dB 사이에서 WER이 **0.100 → 0.300**으로 급격히 올랐습니다(임계 영역 존재) |
| | **WER과 CER은 어떻게 다르게 움직이나?** 10 dB에서 WER 0.300 vs CER 0.171, 5 dB에서 0.560 vs 0.397 — 어절 단위(WER)가 더 가혹함 |
| | **잡음을 제거하면 정말 좋아지나?** (아래: 항상 그렇지는 않음) |
| | **서비스는 어떤 SNR에서 "다시 녹음" 경고를 내야 하나?** 데이터로 **임계값을 정해야** 하는 설계 결정 |
| | **인식 결과가 틀렸을 때 사용자 발음 때문인지 잡음 때문인지** 어떻게 구분하나? |

**이 프로젝트에서의 의미 (핵심)**
- 이 서비스의 점수는 **"인식 일치도"** 입니다(발음 점수가 아님). 그런데 **잡음이 점수를 떨어뜨리면, 사용자는 "내 발음이 나쁘다"고 오해**합니다. 그래서 **잡음이 점수에 주는 영향을 정량화**하고 **그 영향이 큰 구간에서 경고하는 기능**은 서비스의 신뢰성을 위해 필요합니다.
- 연결: L3-b(STT 신뢰 지표)·L3-c(녹음 품질 분류기)가 **"언제 점수를 믿을 수 없는가"** 를 다룹니다. 잡음 실험은 그 **판단 기준의 근거 데이터**를 만듭니다.

**더 의미 있게 만드는 설계 (가설 중심)** **[제안]**
| 가설 | 변수 | 측정 | 서비스 결정에 반영 |
|---|---|---|---|
| H1 잡음이 클수록 오류가 증가한다 | SNR 0~20 dB | WER/CER(3회 이상 평균) | (자명한 확인) |
| H2 오류가 급증하는 **임계 SNR**이 있다 | SNR을 5 dB 간격 또는 더 촘촘히 | 오류 곡선의 꺾이는 지점 | **"SNR ○ dB 미만이면 재녹음 권장"** |
| H3 **잡음 제거를 거치면 오류가 줄어든다** | 제거 전/후 | 같은 SNR에서 비교 | 제거 기능을 넣을지 판단 |
| H4 **흰 잡음 vs 실제 잡음**(카페·거리 녹음)에서 곡선이 다르다 | 잡음 종류 | 같은 SNR에서 비교 | 실제 환경에서의 경고 기준 |

**잡음 제거에 대한 확인 (내가 먼저 해 본 값) [확인, 한계 있음]**
- 강사님이 **"쓸 만한 잡음 제거 모듈이 있다"** 고 하셨다는 내용은 학생 전달 정보이고 **모듈 이름은 모릅니다 [확인 필요: 면담에서 이름을 물어볼 것]**. 후보로 알려진 파이썬 패키지 `noisereduce`가 있습니다 **[일반 지식, 약관·품질은 미확인]**. `pip install --dry-run noisereduce`로 확인해 보니 **`noisereduce-3.0.3`만 설치되고 numpy는 바뀌지 않는 것으로 나왔습니다(현재는 설치 안 됨)** **[확인]**.
- 수업에서 배운 STFT만으로 **아주 단순한 스펙트럼 게이팅**을 직접 만들어 비교해 봤습니다(주파수별로 크기가 낮은 하위 10% 프레임을 잡음으로 추정해 그만큼 빼고, ISTFT로 되돌림). 같은 잡음 시드를 쓴 **제거 전/후 비교**입니다.

  | 조건(시드 동일) | 합산 WER | 합산 CER |
  |---|---|---|
  | SNR 10 dB, 잡음 그대로 | 0.260 (13/50) | 0.164 (24/146) |
  | SNR 10 dB, **간단 스펙트럼 게이팅** | 0.300 (15/50) | 0.185 (27/146) |
  | SNR 5 dB, 잡음 그대로 | 0.620 (31/50) | 0.493 (72/146) |
  | SNR 5 dB, **간단 스펙트럼 게이팅** | 0.700 (35/50) | 0.575 (84/146) |
- **이 단순한 방법은 오류를 줄이지 못했고 오히려 약간 늘었습니다.** 다만 **차이(13→15, 31→35개 오류)는 위 8.10 ⑤에서 본 잡음 시드에 따른 흔들림 범위 안에 있어서 "악화됐다"고 단정할 수 없고, "개선이 관찰되지 않았다"** 가 정확한 표현입니다. 그리고 **내가 만든 단순한 방법의 결과이지 전문 잡음 제거 모듈의 결과가 아닙니다.**
- 일반적으로 잡음 제거가 음성 인식을 **항상 개선하지는 않고**, 제거 과정의 왜곡이 인식에 해가 될 수도 있다고 알려져 있습니다 **[일반 지식, 이 프로젝트에서 확인하지 않음]**. 그래서 **강사님이 말씀하신 모듈로 H3를 실제로 확인하는 것 자체가 비자명한 실험**입니다.
- 소요 시간 참고: 위 비교 4조건에 약 7분이 걸렸습니다(CPU, tiny). 5 dB 잡음 5개 파일에 201초.

**제안: L3 (d) 잡음 견고성 실험**
- 최소 구성(약 4h): **H1 + H2**를 **3회 반복**(SNR 0/5/10/20/깨끗 × 시드 3개), 곡선 그림 1개와 **재녹음 경고 임계값 제안**.
- 확장(약 +2~3h): **H3**(강사님 모듈로 전/후 비교), **H4**(실제 잡음 녹음).

### 8.12 데이터는 언제 필요한가 — 사전학습 모델 활용 vs 직접 학습, L3-c
> 질문: "L3-c 녹음 품질 분류기에는 데이터가 필요한가? 강사님은 내 방식(기존 모델 활용)은 왜 데이터가 필요 없다고 하시나? 모델 학습은 왜 대량의 데이터가 필요한가?"

**1. 두 방식의 차이**
| | 사전학습 모델 활용(내 프로젝트의 중심: Whisper·OpenAI STT/TTS) | 직접 학습(B안, L3-c) |
|---|---|---|
| 하는 일 | 이미 학습된 모델에 입력을 넣어 결과를 받음(추론) | 내 데이터로 가중치를 `fit`으로 바꿈 |
| **학습 데이터** | **필요 없음** — 학습은 이미 끝났습니다 | **필요** — 모델이 데이터에서 패턴을 배웁니다 |
| 그래도 필요한 데이터 | **평가용·시연용 소량**(내 문장, 내 녹음) | 학습용 + 평가용(분리해서) |
| 수업에서의 예 | 7강 Whisper | 6강(작은 LSTM을 문장 3개로 학습) |
- 강사님이 "데이터가 필요 없다"고 하신 것은 **"모델을 학습시키기 위한 데이터"** 를 말씀하신 것으로 이해합니다(학생 전달 정보이며 정확한 맥락은 확인하지 못했습니다 **[확인 필요]**). **평가하고 시연할 문장·녹음은 여전히 필요**하고, 계획서 4장이 바로 그것입니다.

**2. 왜 사전학습 모델은 학습 데이터가 필요 없나 / 왜 학습에는 대량의 데이터가 필요한가**
- Whisper는 **매우 큰 데이터로 이미 학습되었습니다**(공개된 정보로는 수십만 시간 규모의 음성으로 알려져 있습니다 **[일반 지식, 정확한 수치는 확인하지 않음]**). 우리는 그 **결과물(가중치)을 내려받아 쓰는 것**이라, 우리 데이터로 다시 배울 필요가 없습니다(7강: 첫 실행 때 `models/`에 가중치 파일 약 75MB를 내려받은 것).
- 학습에 대량의 데이터가 필요한 이유 **[일반 지식 + 이 저장소에서 본 것]**:
  1. **모델에는 조정할 숫자(가중치)가 매우 많습니다.** Whisper tiny도 수천만 개로 알려져 있습니다 **[일반 지식]**. 데이터가 적으면 이 많은 숫자를 **데이터에 맞게 외워 버립니다(과적합)**.
  2. **일반화**: 목표는 **처음 보는 음성**을 잘 처리하는 것인데, 적은 데이터는 **다양한 목소리·잡음·말투를 담지 못합니다**.
  3. **6강이 그 예**입니다. 문장 3개로 학습한 모델은 **학습한 문장은 잘 맞히지만**(출력에서 정확도 1.0에 도달), 노트북 안내문도 "**학습 자료이므로 시험 성능이 아닙니다**"라고 적고 있습니다. **새 문장·새 음성에서의 성능은 보장되지 않습니다.**
  4. 5강의 **"새 화자 평가를 하려면 학습과 평가 데이터를 분리"** 원칙: 학습에 쓴 데이터로 점수를 매기면 성능이 부풀려지므로 **별도의 평가 데이터**가 또 필요합니다.
- 비유: 학습은 **"외국어를 처음부터 배우는 것"**(많은 문장이 필요), 사전학습 모델 활용은 **"이미 그 외국어를 아는 사람에게 질문하는 것"**(내가 가르칠 필요 없음, 다만 그 사람이 내 상황에서 잘 하는지 시험할 문제는 필요).

**3. L3-c 녹음 품질 분류기는 데이터가 필요한가? → 네, 필요합니다 (소량으로 가능)**
- 직접 학습하는 모델이므로 **학습용 데이터가 필요**합니다. 계획서에는 **클래스(정상/잡음/무음·너무 작음)당 30~40개 [가정]** 으로 잡았습니다.
- **이 정도로 가능한 이유(추정)**: 문제가 **단순한 3분류**이고 클래스 간 차이가 **뚜렷**하며(잡음 유무, 크기), 입력이 Log-Mel로 **요약된 작은 특징**이기 때문입니다. **음성 인식(수만 가지 소리·단어)과는 문제의 복잡도가 완전히 다릅니다.**
- **한계(솔직하게)**: 내 마이크·내 방·내 목소리의 녹음으로만 만들면 **다른 환경에서는 성능이 떨어질 수 있습니다(일반화 부족).** 보고서에 이 한계를 적어야 합니다.
- **데이터를 줄이는 방법**: ① 문제를 단순하게(2분류), ② **전이학습**(007 MobileNetV2처럼 이미 학습된 부분을 재사용, **[일반 지식]**: 새로 학습할 부분이 작아져 적은 데이터로 가능), ③ 반복 녹음 시 **세션을 나눠서 학습/평가에 섞이지 않게**(5강 원칙). 직접 만들기 어려우면 **L3-c는 건너뛰고 (a)(b)(d)만** 해도 충분히 깊이가 있습니다.
- 반대로 **"모델 학습 경험" 자체가 목적이 아니라면** 내 주제의 중심(사전학습 모델 활용 + 평가 설계)이 오히려 **데이터 부담이 적고 깊이는 실험 설계에서** 만들어집니다.

### 8.14 상업 노래의 가사·음원을 쓰면 안 되는 이유와 대안 (2026-10-30)
> 질문: "왜 상업 노래의 가사·음원을 사용하면 안 되나? 예를 들어 aespa의 일본 발매 일본어 노래 가사를 인터넷에서 스크래핑해서 쓰면 안 되나?"
> 아래는 법률 자문이 아니라 일반적인 저작권 상식입니다. 한국과 일본의 법이 다를 수 있어 법적으로 확정하려면 확인이 필요합니다 **[일반 지식, 확인 필요]**.

**1. 왜 안 되나**
- **가사는 저작물**입니다. 작사가·출판사 같은 권리자가 있고, 허락 없이 **복제하거나 공개(전송)** 하는 것은 제한됩니다. 인터넷에 떠 있어도 "누구나 써도 된다"는 뜻은 아니고, 가사 사이트는 **권리자와 계약해서** 보여 주는 것입니다. 일본어로 발매된 곡이면 일본 쪽 권리 관리 체계(JASRAC 같은 관리단체)가 적용될 가능성이 큽니다 **[확인 필요]**.
- **스크래핑에는 별도 문제**가 있습니다. 사이트 **이용약관이 수집을 금지**하는 경우가 많고, 가사 데이터베이스를 통째로 가져오는 것도 문제가 될 수 있습니다. 현실적으로도 사이트 구조가 자주 바뀌어 **깨지기 쉽고**, 36시간 중 상당 시간을 수집 코드에 쓰게 되어 프로젝트의 핵심(채점·실험)과 거리가 멉니다.
- **프로젝트에서는 "어디에 두느냐"가 핵심**입니다.

  | 상황 | 위험 |
  |---|---|
  | 내 컴퓨터에서 혼자 연습 | 비교적 낮음(그래도 약관·사적 이용 범위는 확인 필요) |
  | **공개 GitHub 저장소에 가사 파일·문장 올리기** | **복제·공개에 해당, 가장 큰 문제** |
  | 발표·시연 화면에 가사 전체 표시 | 공개에 해당할 수 있음 |
  | 가사를 OpenAI TTS·LLM API로 전송 | 외부 서비스 약관 확인 필요 |
  | 원곡 음원 파일을 저장소·실험에 포함 | 음원도 저작물, 같은 문제 |
- 이 저장소는 **public**이고, 이미 내 목소리·강사님 자료는 올리지 않는 원칙을 지키고 있어 같은 기준을 가사에도 적용한 것입니다.

**2. 내 아이디어를 살리는 방법**
1. **사용자가 입력한 텍스트를 처리하는 구조**로 설계: 서비스가 가사 DB를 들고 있지 않고, 사용자가 자기 문장을 입력해 연습합니다.
2. **시연·저장소·발표에는 직접 쓴 예문**: 노래에서 영감받은 표현으로 내가 만든 문장(현재 계획서의 방식).
3. **퍼블릭 도메인 노래**(전통 동요·민요 등)는 L3 노래 구간 실험(a)에 사용 가능 — **판본과 국가별 상태 확인 필요**.
4. **가사 API는 확장 아이디어로만**: 라이선스된 가사 API가 있지만 키·약관·요금·지원 언어가 불확실해 36시간 계획에 넣기 위험합니다.
5. **아티스트는 "동기(배경)"로만 언급**: 발표에서 "이런 노래를 배우고 싶어 시작했다"고 말하는 것은 가사 내용을 표시하는 것과 다릅니다.
- **짧은 구절 인용**은 법에서 "정당한 범위의 인용"으로 허용될 수 있다고 알려져 있으나(한국 저작권법의 인용 규정) 범위 판단이 어렵고, **가사 수집 코드와는 별개**라서 계획에 넣지 않았습니다 **[일반 지식, 확인 필요]**.
- 계획서 반영: **"LLM에 상업 가사 전문을 입력·저장하는 것"을 범위 제외**에 명시, LLM 설명은 **직접 쓴 연습 문장에만** 적용(8.17).

### 8.17 계획서의 LLM 기능 추가에 대한 검토와 A안 결정 (2026-10-30)
> 질문: "내가 계획서를 일부 수정했다(배경에 LLM으로 가사의 뜻·연관 단어·표현 학습 추가, 성공 기준 공통 행에서 개인 음성·key 문구 삭제). 검토해 달라."

**바뀐 내용 3곳**: ① 배경에서 "내 발음이 맞는지 확인하기 어렵습니다"를 빼고 LLM 학습 문장을 추가 ② 성공 기준 '공통' 행에서 "개인 음성·API key가 저장소에 없음" 삭제 ③ "참고(이미 확인한 값)" → "참고".

**검토**
- ③은 문제없음. ②는 괜찮음(제품 성공 기준이라기보다 보안 점검 항목이며 4·7·9장에 남아 있음) → **9일차 "최종 점검" 체크 항목으로 옮김**(요청 반영).
- ①은 보완이 필요했음:
  - **문제 진술 삭제**: "확인하기 어렵다"는 이 도구가 필요한 이유(문제 정의)라 한 구절은 되살릴 것.
  - **LLM 기능이 배경에만 있고 나머지 문서와 불일치**: 범위 L2는 "한국어 뜻 표시(직접 작성)", 기술 스택엔 OpenAI 채팅(LLM) 없음, 프로그램 구조·성공 기준·일정에도 없음. 본문 `LLM`은 "계획서 작성 보조 도구"로만 쓰여 같은 단어가 다른 뜻으로 쓰임.
  - **"가사"** 표현이 "상업 가사는 쓰지 않는다"는 방침과 충돌 → "연습 문장"으로.
  - **LLM이 만든 뜻·표현은 틀릴 수 있음** → 검수 방법(직접 확인한 문장 수·오류 기록)과 "AI 생성(참고용)" 표시 필요, 가사를 외부 API로 보내는 약관도 확인 대상(8.14).
  - **일정·한도 부담**: key 한도를 모르는 상태에서 LLM 호출이 추가되면 L2 작업이 늘어남.
- **선택지**: A) L2 항목으로 정식 반영(범위·기술 스택·구조·성공 기준·일정·위험·검증 모두) / B) 배경에만 두고 "확장 아이디어"로 격하. → **A안으로 결정**, 계획서에 반영(LLM 뜻·표현 설명은 L2, 직접 검수 기록, 지연 시 가장 먼저 제외).
- 한 가지 주의: **6일차에 기록·그래프와 LLM 설명(검수)이 함께 있어 빠듯할 수 있음**. 축소 규칙에 LLM을 가장 먼저 빼도록 했고, 5일차로 일부 이동하는 방법도 있음.

### 8.18 계획서에 FFT·STFT·Log-Mel 내용을 추가·보완할 곳 (2026-10-30)

- **16개 중 복습·활용 12개, 새로 배우는 것 4개**(WER/CER, `difflib`, 언어별 정규화, (b))이고, 그 밖에 **확장으로 둔 새 도구**(잡음 제거 모듈, 웹 화면은 아예 기본 범위에서 뺐음)가 있습니다.
- **좋은 점**: 핵심 흐름(L1)은 013·7강·1~5강으로 거의 채워져 있고, **새로 배우는 필수 항목은 WER/CER 하나**(이미 구현·검증)입니다.

**2. 방향이 안 보이는 곳 / 위험**
1. **방향 문장이 없습니다.** 개요(목적·SMART)에는 "수업(7강·013·1~4강)을 활용하고 WER/CER을 자습으로 보완"한다는 한 줄(Relevant)이 있을 뿐, **"복습·활용 중심, 새 시도는 최소"** 라는 원칙과 **새 시도의 한도**는 없습니다.
2. **범위가 넓습니다.** L1~L3와 최근 추가(품질 점검, 스펙트로그램)까지 합치면 **9일 36h(버퍼 없음)** 에 비해 많아서 **지연되면 새 도구를 급히 배우게 될 위험**이 있습니다.
3. **"지난 6주" 중 일부만 쓰입니다.** 계획이 쓰는 것은 **013, 1~7강, 앞 수업의 Pandas·matplotlib**이고, **014~016(LangChain·LangGraph·RAG), CNN·전이학습(007), RNN/Seq2Seq/Attention/Transformer**는 거의 쓰이지 않습니다. 이 전부를 복습하는 것이 목표라면 현재 계획은 **음성 쪽 수업의 복습에 치우쳐** 있습니다(목표가 "음성 과정 복습"이면 문제 아님 → **확인 필요**).
4. **L2의 LLM 설명(11번)** 은 013 호출로 가능하지만 **새 기능 + 검수 작업**이라 "새 시도 최소" 원칙과는 긴장이 있습니다.
5. **L3 (b)·(d)의 잡음 제거 모듈**은 수업에 없는 도구/필드(`avg_logprob` 등)라 원칙과 맞지 않습니다(확장·선택으로만 두는 것이 맞음).

### 8.21 외부 검토(ChatGPT) 결과와 내 의견, 계획서 반영 (2026-10-30 저녁)

**입력**: ChatGPT가 GitHub `main`(README·계획서·검토 문서·5~7강 노트북)을 읽고 쓴 검토문(로컬 txt, 약 1,790줄, 코드를 직접 실행하지는 않음)입니다. 뒷부분에는 계획과 직접 관련 없는 대화(재생 제어, SNR 설명, 리샘플링, 사운드 아트 아이디어)도 이어집니다. **표시 규칙**: **[확인]** = 이번에 직접 실행·확인, **[일반 지식]** = 확인하지 않은 일반 내용, **[추정]** = 제 해석.

**총평(두 의견 공통)**: 수업 기록은 체계적이고 계획서는 쓸 만하다. 다만 **기능을 더 넣기보다 이미 정한 핵심 흐름을 정확히 정의하고 끝까지 완성**하는 것이 중요하다. 이 판단에 동의합니다.

#### 2. ChatGPT 검토에서 내가 확인하지 못했거나 조심할 점

- 검토문의 일부 이미지·링크는 외부 사이트 자동 삽입이라 근거로 쓰지 않는다.

**왜 이렇게 쓰는가 (근거)**

**직접 해볼 확인 (사용자가 실행, 결과를 알려 주면 해석을 돕습니다)** — 아래 셀을 `jupyter notebook`과 VS Code에서 각각 실행해 버튼이 동작하는지 봅니다. 내가 브라우저에서 돌려 보지 않았으므로 **동작 여부는 미확인**입니다.

```python
import base64
from IPython.display import HTML, display

def player_html(wav_path):
    b64 = base64.b64encode(open(wav_path, "rb").read()).decode()
    A = "this.parentNode.querySelector('audio')"          # 이 플레이어 묶음 안의 <audio>
    speeds = [0.75, 0.9, 1.0, 1.1, 1.25]
    options = "".join(f'<option value="{v}"{" selected" if v == 1.0 else ""}>{v}×</option>' for v in speeds)
    return f"""
    <div>
      <audio controls style="width:100%" src="data:audio/wav;base64,{b64}"></audio><br>
      <button onclick="var a={A}; a.currentTime=0; a.play()">처음부터</button>
      <button onclick="var a={A}; a.currentTime=Math.max(0, a.currentTime-5)">-5초</button>
      <button onclick="var a={A}; a.paused ? a.play() : a.pause()">재생/일시정지</button>
      <button onclick="var a={A}; a.currentTime=Math.min(a.duration||1e9, a.currentTime+5)">+5초</button>
      속도 <select onchange="this.parentNode.querySelector('audio').playbackRate=parseFloat(this.value)">{options}</select>
    </div>"""

display(HTML(player_html("data/speech/<제공된 wav 파일 이름>.wav")))
```
확인할 것: ① 버튼 4개가 동작한다 ② 속도를 0.75×로 바꾸면 재생이 느려지고 **목소리 높낮이가 크게 변하지 않는다**(귀로 확인) ③ 일시정지 후 위치가 유지된다 ④ VS Code에서도 같다. 안 되면 계획서의 대체안(기본 `Audio`)으로 갑니다. 이 셀의 출력은 오디오가 base64로 박히므로 **커밋하기 전에 출력을 지웁니다.**

#### 1. 제목의 "프로토타입"은 무슨 뜻인가
- **노트북에서 실제로 동작하는 시제품**이라는 뜻입니다. 핵심 흐름(듣기 → 읽기/받아쓰기 → 채점)이 되는지 직접 만들어 보고 한계를 확인하는 것이 목표이고, 앱 배포·화면 완성도·다수 사용자 서비스는 목표가 아닙니다.
- 이 단어를 쓴 이유: ① 36시간·노트북 시연이라는 규모를 정직하게 표현하려고 ② 점수가 발음 점수가 아니라 "문장 인식 일치도"라서 완성된 평가 서비스로 오해받지 않게 ③ ChatGPT도 "서비스와 MVP의 차이를 명시"하라고 권했습니다(8.21의 1번).
- 어감이 마음에 안 들면 "시연 도구" 같은 말로 바꿔도 내용은 같습니다.

#### 2. "30건 처리 + 손계산 5건"과 "정규화"가 정확히 무엇인가
**검토 문서 어디에 있나**: 7절(WER/CER 구현과 검증 코드), 8.21(외부 검토), 8.22의 3번(성공 기준 용어 풀이)에 있습니다. 구체 데이터로 직접 보려면 **`WER_CER_이해하기.ipynb`** 가 가장 쉽습니다(표 채우기 → 역추적 → WER/CER → 정규화 순서).

**(1) 30건 = 10문장 × 3회**: 같은 문장을 세 번씩 읽어 녹음한 파일 30개를 프로그램에 넣었을 때 **중간에 멈추지 않고 끝까지 결과를 내는지** 보는 것입니다(처리 성공). 인식이 정확한지는 별개입니다.

**(2) 손계산 5건**: 정답/인식 문장 5쌍을 **내가 종이로 계산**해서 코드 결과와 비교합니다. 즉 **채점 코드가 맞는지 검증**하는 장치입니다. 예: 정답 `the cat sat on the mat`, 인식 `the cat sit on mat` → 치환 1(`sat`→`sit`) + 삭제 1(`the`) = 2, 정답 6단어 → WER = 2/6 = 0.333 **[확인]**. 5쌍은 서로 다른 유형을 하나씩 고르는 것을 제안합니다 **[제안]**:
1. 완전 일치(0.0) 2. 치환만 3. 삭제만 4. 삽입이 많아 WER > 1 5. 정규화가 필요한 쌍(대소문자·구두점)

**(3) 정규화 = STT가 낸 문장과 정답을 비교하기 전에 형식을 같은 규칙으로 맞추는 일**입니다. 소리를 같게 들었어도 대소문자·구두점·공백이 다르면 단어가 다르다고 세기 때문입니다. 아래는 직접 계산한 값입니다 **[확인]**.

| 상황 | 정답 / 인식 | 정규화 전 | 정규화 후 |
|---|---|---|---|
| 대소문자·구두점 | `I want to explore the universe.` / `i want to explore the universe` | 2/6 = 0.333 | 0/6 = 0 |
| 연속 공백 | `Hello,   world` / `Hello world` | 1/2 = 0.5 | 0/2 = 0 |
| 축약형 | `Don't stop believing!` / `do not stop believing` | 3/3 = 1.0 | 2/3 = 0.667 (`don't`≠`do not`은 규칙을 정해야 함) |
| 숫자 | `I have 2 cats` / `i have two cats` | 2/4 = 0.5 | 1/4 = 0.25 (`2`≠`two`는 규칙을 정해야 함) |
| 프랑스어 악센트 | `Où est la gare ?` / `ou est la gare` | 2/5 = 0.4 | 악센트 유지 1/4 = 0.25, **악센트 제거 0/4 = 0** |
| 유니코드 NFC/NFD | `café au lait` 두 가지 내부 표현(눈에는 똑같이 보임) | 1/3 = 0.333 | NFC로 맞추면 0/3 = 0 |
| 일본어(글자 단위 CER) | `今日は天気がいいです。` / `今日は天気が良いです` | 2/11 = 0.182 | 1/10 = 0.1 (`いい`↔`良い` 표기 차이는 남음) |
| 일본어 | 같은 문장을 히라가나로 쓴 `きょうはてんきがいいです` | 7/11 = 0.636 | 6/10 = 0.6 (같은 뜻인데 크게 틀린 것으로 셈) |

- **실제 Whisper 결과(수업 제공 WAV, tiny, 로컬)** **[확인, 참고 baseline]**: 정답 `…친구와 도서관에 가서 오늘 …` vs 인식 `…끝나면, 친구와 도서관에 가서, 오늘 …`처럼 **쉼표만 붙어도 단어가 달라져** 정규화 전 WER 0.200, 구두점을 지우면 0.000이었습니다. 5개 합산은 구두점을 지웠을 때 WER 0.060 / CER 0.034, 지우지 않으면 WER 0.200(7절 값과 같음).
- 결론: **점수를 바꾸는 것은 인식 실력이 아니라 규칙**일 수 있으므로, 규칙을 **하나로 고정해 문서화**하고(= 계획서의 "정규화 규칙 문서"), 규칙을 너무 많이 적용해 실제 인식 실수까지 가리지 않도록 주의합니다. 어떤 규칙이 "정답"인지는 없고 일관성이 중요합니다 **[추정]**.

#### 3. FFT·STFT·스펙트로그램·Mel 보완 — 녹음 입력 상태를 판단하는 방법론이 있는가
**계획서에 반영한 것**: 2장 끝에 "1~4강 활용 지점" 표, 3장에 "녹음 입력 상태 점검 방법" 표(기준값은 초안, 1일차에 내 녹음으로 확정).

**방법론(크게 네 갈래)** **[일반 지식 + 아래 실험]**
1. **파형 통계**: RMS(전체 음량), 최대 진폭, 클리핑 비율(절댓값이 1에 붙은 샘플 비율), 길이.
2. **프레임 기반(STFT)**: 짧은 구간(프레임)마다 에너지를 구해 **말이 있는 프레임과 조용한 프레임**을 나눕니다 → 무음 비율, 그리고 조용한 프레임의 에너지로 **배경 잡음 수준**을 추정할 수 있습니다.
3. **스펙트럼 기반(FFT)**: 주파수별 에너지를 봅니다 → 저주파 웅웅거림(예: 80 Hz 이하 비율), 실제로 쓰인 **대역폭**(99% 에너지가 들어 있는 상한 주파수).
4. **거친 SNR 추정 / 학습 기반**: 조용한 프레임을 잡음, 큰 프레임을 말로 보고 비를 계산하는 방식, 또는 L3-(d)처럼 분류기를 학습하는 방식. VAD(말 구간 검출) 도구도 있습니다 **[일반 지식]**.

**수업 제공 WAV 1개로 확인한 값** (16 kHz, STFT 512/hop 128/hann, 같은 파일에 변형을 가함) **[확인, 참고 baseline]**

| 조건 | RMS(dBFS) | 클리핑 | 무음(절대 −60 dB) | 무음(상대 −35 dB) | 99% 대역폭 | 거친 SNR 추정 |
|---|---|---|---|---|---|---|
| 원본 | −19.2 | 0% | 22.7% | 15.0% | 1953 Hz | 66 dB |
| 0.02배로 작게 | −53.2 | 0% | **100%** | 15.0% | 1953 Hz | 45 dB |
| 8배로 키워 잘림 | −4.6 | **20.8%** | 14.5% | 14.4% | 3314 Hz | 62 dB |
| 흰 잡음 20 dB | −19.2 | 0% | 21.0% | 0% | 3483 Hz | 24 dB |
| 흰 잡음 10 dB | −18.8 | 0% | 0% | 0% | 7215 Hz | 14 dB |
| 흰 잡음 5 dB | −18.0 | 0% | 0% | 0% | 7684 Hz | 9 dB |

여기서 읽을 수 있는 것
- **절대 기준 무음은 작게 녹음된 파일을 전부 무음으로 오판**합니다(100%). **상대 기준**(가장 큰 프레임보다 35 dB 이상 낮은 프레임)은 음량과 무관하게 15%로 안정적이었습니다 → 계획서에 상대 기준을 넣었습니다.
- **클리핑은 클리핑 비율이 가장 직접적인 지표**이고, 잘리면 대역폭도 넓어집니다(1953 → 3314 Hz).
- **흰 잡음이 늘수록 99% 대역폭이 올라가고(→ 7 kHz대) 상대 무음 비율이 0이 됩니다.** 다만 **흰 잡음 특성이라 실제 환경 잡음(에어컨 등 저주파)은 다를 수 있습니다 [추정]**.
- **정정**: 앞서 "녹음 하나로는 SNR을 알 수 없다"고 한 표현은 **너무 강했습니다.** 조용한 프레임 하위 10%와 큰 프레임 상위 30% 에너지로 계산한 **거친 추정**이 알려진 SNR을 **단조롭게 따라갔습니다**(5개 파일 × 시드 3개 평균: 20 dB → 24.1, 10 → 14.2, 5 → 9.3, 0 → 4.5, 대략 +4 dB 치우침). 하지만 ① 합성 흰 잡음·수업 제공 합성 음성 5개에 한정되고 ② 원본이 완전한 무음 구간을 가져 추정이 46~66 dB로 비현실적이며 ③ 실제 녹음은 배경 소음 때문에 결과가 다를 것이라 **서비스 경고 기준으로 쓰기에는 검증이 필요**합니다. 그래서 계획서는 "정확히 판정하는 기능은 만들지 않는다"로 유지하고, **(e)의 확장 후보**로 "거친 SNR 추정이 실제 녹음에서도 통하는가"를 둘 수 있습니다 **[제안]**.

**직접 해볼 확인 (내 녹음에 적용)**
```python
import numpy as np
from scipy.io import wavfile
from scipy.signal import stft

sr, x = wavfile.read("data/<내 녹음>.wav")          # 16-bit PCM WAV
x = x.astype(np.float32) / 32768.0
if x.ndim > 1: x = x.mean(axis=1)                    # 스테레오 → 모노

rms_db = 20 * np.log10(np.sqrt((x ** 2).mean()) + 1e-10)
peak = np.abs(x).max()
clip = (np.abs(x) >= 0.999).mean()

f, t, Z = stft(x, fs=sr, nperseg=512, noverlap=384, window="hann")
frame_db = 10 * np.log10((np.abs(Z) ** 2).mean(axis=0) + 1e-12)   # 프레임별 에너지(dB)
silent_rel = (frame_db < frame_db.max() - 35).mean()               # 상대 기준 무음 비율

spec = np.abs(np.fft.rfft(x)) ** 2; fr = np.fft.rfftfreq(len(x), 1 / sr)
low_hum = spec[fr < 80].sum() / spec.sum()
rolloff99 = fr[np.searchsorted(np.cumsum(spec) / spec.sum(), 0.99)]
print(rms_db, peak, clip, silent_rel, low_hum, rolloff99)
```
확인할 것: 조용한 환경에서 읽은 녹음과 일부러 작게 읽은 녹음, 일부러 크게 외친 녹음, 카페 소음 녹음에서 위 값이 어떻게 달라지는지. 그 결과로 3장 표의 경고 기준을 확정합니다.

#### 4. L2 HTML 플레이어는 어떻게 노트북에 넣는가
- **HTML 파일 링크를 거는 방식이 아닙니다.** 파이썬 함수(`player.py`)가 `<audio>`와 버튼이 들어 있는 **HTML 문자열을 만들고**, 노트북 셀에서 `display(HTML(...))`를 실행하면 **그 셀의 출력 영역에 플레이어가 그려집니다.**
- 음원은 base64로 HTML 안에 넣기 때문에 파일 경로·서버가 필요 없습니다(8.22의 코드 참고). 단점: 노트북 파일이 커지고, 커밋할 때 출력을 지워야 합니다.
- 수업 자료에서 강사님이 별도 HTML 파일로 설명을 보여 주셨는지는 제가 정확히 확인하지 못했습니다 **[미확인]**. 어떤 방식이든 이 프로젝트의 플레이어는 위처럼 "셀 출력"이 기본입니다.
- 동작은 VS Code 노트북에서 **[미확인]**이라 5일차 전에 10분 테스트하고, 안 되면 기본 `Audio` 플레이어로 대체합니다(계획서에 있음).

#### 5. "연습 기록 저장(CSV)·오류율 그래프"는 무엇이고 DB가 필요한가
- **WER/CER 노트북에는 없는 내용**이고, **이 프로젝트를 위해 제가 설계한 기능**입니다. 개념 자체는 새로운 것이 아니라 "학습 기록(learning log)/실험 로깅"이라는 흔한 패턴입니다 **[일반 지식]**. 과제의 필수 요건이 아니고, 일정이 밀리면 제외 순서에도 들어 있습니다.
- **무엇을 저장하나(예시)**: 연습 1회마다 한 줄 — 시각, 문장 id, 모드(읽기/받아쓰기), 인식 결과, WER, CER, 치환·삭제·삽입 수, STT 모델·설정, 입력 상태 경고 여부.
- **그래프**: 같은 문장을 반복할수록 오류율이 줄어드는지, 문장별 평균 오류율이 어떻게 다른지.
- **의미**: ① 사용자가 연습 진행을 확인(학습 서비스의 핵심 가치) ② 개발자가 **설정(모델, 규칙)과 함께 결과를 남겨 재현 가능하게** 비교 ③ L3-(c) 같은 분석의 **데이터 원천**. 실제 음성 AI 서비스에서도 인식 결과·설정을 로그로 남겨 품질을 추적하는 것은 일반적입니다 **[일반 지식]**.
- **DB는 필요 없습니다.** 사용자 1명, 로컬 실행, 기록 수백 건이면 CSV(Pandas)로 충분합니다. DB는 다중 사용자·동시 접근·서버가 있을 때(예: PWA) 필요합니다 **[일반 지식]**. 쓰고 싶다면 표준 라이브러리 `sqlite3`가 가장 가볍지만 "새 시도 최소" 방향상 CSV를 권합니다.

#### 6. 음악·음성 분리와 가사 추출을 L3 첫 번째로
- **동의하고 반영했습니다.** L3 (a)를 "노래 구간 인식 + 음악·음성 분리"로 하고 첫 번째 선택지이자 기본안으로 바꿨습니다(언어 추가는 (b)로). 이유: 강사님이 권유하셨고, 네 시작 동기와 맞으며, 앞서 만든 STT·WER/CER·스펙트로그램 도구를 그대로 쓰기 때문입니다.
- **실험 설계(제안)**: 직접 부른 노래 + 저작권 문제 없는 반주를 섞은 샘플을 만들면 **섞기 전 원본 음성을 알고 있어** 분리 결과를 정답과 비교할 수 있습니다. 비교 대상은 ① 낭독 ② 노래(반주 없음) ③ 노래+반주(분리 전) ④ 분리 후 보컬. 각각 Whisper로 인식해 CER을 비교하고 스펙트로그램도 그립니다. "가사 추출"은 서비스 기능이 아니라 이 **실험의 결과 측정**으로 다룹니다(제외 사항과 일치).
- **상업 음원은 쓰지 않습니다**(저장소 공개, 계획의 규칙). 반주는 직접 만들거나 이용이 허용된 무료 음원으로 하고 이용 조건을 기록합니다.
- **확인한 것/못 한 것**: `pip install --dry-run demucs` 결과 **demucs 4.1.0 외 einops·julius·lameenc·safetensors·sphn만 추가되고 numpy·torch는 바뀌지 않았습니다 [확인]**. 하지만 **CPU(Intel i7 4스레드)에서 몇 배속으로 도는지, 모델 파일 크기와 다운로드 시간은 확인하지 못했습니다 [미확인]**. 그래서 계획서에 "10~20초 구간만, 안 되면 분리 없이 낭독 vs 노래 비교만" 위험 대응을 넣었습니다. 사용자가 짧은 구간으로 직접 설치·실행해 보기를 권합니다(예: `%pip install demucs` 후 짧은 wav 하나; 명령줄 옵션은 Demucs 문서를 확인).

**(c)와 (e)가 무엇인지** (검토 문서 전체를 읽을 필요는 없습니다. 아래로 충분하고, 더 보려면 8.11·8.12)
- **(c) STT 신뢰 지표 vs 실제 오류**: Whisper는 결과와 함께 "모델이 얼마나 확신하는지"를 숫자로 줍니다(`avg_logprob`: 0에 가까울수록 확신, `no_speech_prob`: 말이 없다고 보는 확률 등). 실제 서비스에서는 정답이 없으니 이 숫자가 **낮을 때 실제 오류도 높은가**를 내 기록 30건 이상으로 확인해, 맞다면 "신뢰도가 낮으니 다시 녹음해 보세요"라는 안내의 근거로 씁니다. 즉 "숫자가 쓸모 있는지 검증하는 분석"입니다.
- **(e) 잡음 견고성**: 깨끗한 녹음에 **일부러 잡음을 정해진 세기(SNR: 신호 대 잡음비, 값이 낮을수록 잡음이 큼)로 섞어**, 잡음이 늘수록 Whisper 오류율이 어떻게 변하는지 곡선으로 그립니다. 내가 한 번 돌린 참고 baseline은 깨끗한 원본 WER 0.060, 20 dB 0.100, 10 dB 0.300, 5 dB 0.560, 0 dB 0.960 입니다(8.11, 시드에 따라 흔들림). 의미: **점수가 낮은 것이 발음 때문이 아니라 잡음 때문일 수 있다**는 근거를 만듭니다.

#### 7. 11/11까지 PWA로 배포해 아이폰에서 쓰는 것이 가능한가
**결론: 가능성은 있지만 현재 36시간 계획에는 넣지 않는 것을 권합니다 [추정].** 이유와 선택지를 정리합니다(결정은 사용자).

- **필요한 것**: ① 프론트: 마이크 녹음(브라우저 `MediaRecorder`), 오디오 재생, 화면 ② 백엔드: TTS 호출, STT(서버에서 faster-whisper 실행), 채점 API ③ HTTPS(브라우저 마이크는 HTTPS 필요) ④ API key를 서버에 보관 ⑤ PWA 설정(manifest, 홈 화면 추가) ⑥ iPhone Safari/PWA 특유의 오디오·마이크 제약 **[일반 지식, 미확인]**. 사용 중인 Oracle 서버의 CPU·메모리로 Whisper를 돌릴 수 있는지는 **모릅니다 [미확인]**.
- **시간**: AI 도움을 받아도 iPhone 녹음 형식 문제 등 디버깅까지 포함하면 **대략 12~20시간 [추정]**이라, L1~L2를 마치고 L3 시간을 전부 써야 합니다.
- **방향과의 충돌**: "복습 중심, 새 시도 최소" 방향, 그리고 강사님 평가 기준(DNN/CNN/RNN/OpenAI API 범주, 미확정)과 충돌할 수 있습니다.

| 선택지 | 내용 | 평가 |
|---|---|---|
| A. 노트북 프로토타입(현재) | 시연은 노트북, 녹음은 iPhone으로 한 뒤 파일을 Mac으로 옮겨 처리 | 안전. 36시간 안에 완성 가능 |
| B. 6일차까지 L1·L2를 끝낸 경우에만 얇은 웹 | FastAPI 한 개 + 단일 페이지(L3 대신) | 일정이 빠듯하고 서버 사양 확인 필요 |
| C. 프로젝트 이후 확장 | 모듈(`tts.py`, `stt.py`, `scoring.py`)을 그대로 API로 감싸 PWA로 | 모듈 분리 설계 덕에 가능, 위험 가장 낮음 |

**권장**: A로 진행하고 C를 후속으로 둡니다. B는 4일차 L1 완료 시점에 진행 상황과 서버 사양을 보고 다시 판단합니다.

#### 8. "제외될 사항"의 세 줄이 무슨 뜻인가
- **"녹음 하나에서 SNR을 자동 추정하거나 잡음 여부를 판별하는 기능"**: 사용자가 녹음 파일 한 개를 넣었을 때 프로그램이 "이 녹음은 잡음이 많다/SNR이 몇 dB다"라고 **믿을 만하게 판정해 주는 기능은 만들지 않는다**는 뜻입니다. 3번 실험처럼 거친 추정은 가능하지만 검증되지 않았기 때문입니다.
- **"입력 상태 점검은 음량·무음·클리핑만 다룸"**: 대신 L1에서 하는 점검은 소리가 너무 작은지, 대부분 조용한지, 소리가 잘렸는지만 본다는 뜻입니다. "잡음 검사"가 아닙니다.
- **"잡음 실험은 합성 white noises와 소수 문장에 한정"**: 이것은 **제외 사항이 아니라 실험의 한계**입니다. (e) 실험은 컴퓨터가 만든 흰 잡음과 몇 개 문장으로만 했으므로 "실제 카페 소음에서도 같다"고 말하지 않는다는 뜻입니다.
- 한 문단으로 묶으면 헷갈리므로 **계획서에서 두 항목으로 나누어 쉬운 말로 바꿨습니다.**

#### 9. 편집 거리는 WER/CER 노트북에 있는가
있습니다. **2절**(편집 거리 표 직접 채우기)과 **3절**(역추적), 8절(`difflib`와의 차이)이 편집 거리 내용입니다. 따로 추가하지 않았습니다.

#### 10. 데이터 흐름의 `sentences.csv`는 왜 있는가 (사용자가 노래 문장을 입력하는 컨셉과의 관계)
- **고정된 연습 문장 목록은 "프로그램이 검증된 뒤 UI로 바꾼다"는 단계 구분이 아니라, 평가를 재현하려는 장치**입니다. 같은 10문장을 3회씩 읽어야 손계산 검증, 규칙 A/B/C 비교, 기록 그래프가 가능합니다. 문장 메타(출처·라이선스·뜻)도 거기에 둡니다.
- **사용자가 직접 문장을 입력하는 것은 L1에서도 됩니다.** 함수에 문자열 하나를 넣으면 TTS·채점이 그대로 동작하기 때문입니다. 계획서 3장에 "CSV에서 고르거나 직접 입력 가능, 직접 입력은 평가 지표에서 제외"라고 한 줄 추가했습니다. 실제 앱 UI(문장 입력 화면)는 프로토타입의 범위 밖이고 후속(7번의 C)입니다.

#### 11. 연습 문장을 10개로 한 근거
- **통계적 근거는 없습니다.** 제 판단으로 **작업량 기준**을 잡은 것입니다 **[추정]**: 문장당 3회 녹음(30건) + 손검수 + 정규화 규칙 비교를 36시간 안에 끝낼 수 있는 크기입니다. 10개로는 일반화된 성능을 주장할 수 없고, 이 프로젝트는 "일반 성능"이 아니라 **채점 흐름의 검증과 규칙·조건에 따른 변화 관찰**이 목적입니다.
- 문장 설계 기준(초안)을 계획서에 넣었습니다: 5~12단어, 축약형 2~3개, 비슷하게 들리는 단어 쌍 1~2개, 숫자는 규칙을 정하기 전까지 제외. 이렇게 하면 10개 안에서 정규화와 오류 유형이 골고루 나옵니다.
- 늘리고 싶다면 15개도 가능하지만 녹음·검수 시간이 비례해 늘어납니다.

#### 12. "정규화 규칙 문서" = `scoring.py`인가
아닙니다. **문서**는 사람이 읽는 **규칙 표와 예시**(위 2번의 표 같은 것, `md` 또는 README 한 절)이고, **`scoring.py`는 그 규칙을 구현한 코드**입니다. 둘이 어긋나지 않게 **문서의 예시를 `scoring.py` 테스트에 그대로 넣어** 검증합니다(계획서 5장에 반영).

#### 13. 위 답변이 L2 포기 순서에 영향을 주는가
- **순서는 그대로 두었습니다**: ① LLM 뜻·표현 → ② 재생 속도·±5초(기본 플레이어로 대체) → ③ 오류율 그래프 → ④ 기록 CSV, **받아쓰기는 마지막까지 유지**.
- 근거: LLM은 새 기능 + 검수 비용이라 학습 사이클의 핵심이 아니고, 재생 제어는 JS 동작이 불확실하지만 대체안이 있으며, 그래프는 기록이 있으면 나중에 그릴 수 있고, **기록 CSV는 1시간이면 되고 (c) 분석·재현 로그의 원천이라 가장 늦게 뺍니다.**
- 바뀐 점은 **L3 기본안이 (a)로 바뀌었으므로**, L2가 6일차까지 끝나지 않으면 L3는 (a)의 최소 구성(분리 없이 낭독 vs 노래 CER 비교)만 하고 막히면 (e)로 대체한다는 문구입니다.

#### 14. 이번에 계획서에서 바꾼 것 요약
프로토타입 정의 한 줄, L3 (a)↔(b) 교체와 (a) 설명 확장(분리 전/후, 데이터, 일정 8h), 권장 조합과 7일차·축소 규칙, 기술 스택에 분리 모델 행과 "1~4강 활용 지점" 표, 3장에 `sentences.csv` 설명과 "입력 상태 점검 방법" 표, 4장에 노래 샘플 행·문장 수 근거·설계 기준, 5장 정규화 규칙 문서 설명, 7장 위험 1행 추가, 제외 사항 문구 정리, 성공 기준 L3 예시. 실제 개발은 **네가 읽고 확정한 뒤** 시작합니다.
